## 关键技术点

XSLT（Extensible Stylesheet Language Transformations）是一种基于 XML 的样式表转换语言，历史上常用于把 XML 文档在浏览器端转换为 HTML、SVG 或纯文本输出。网页可以通过 `<?xml-stylesheet?>` 处理指令，让浏览器加载 XSLT 对 XML 做客户端转换。Chromium 系浏览器长期内置了对应的 XSLT 处理能力。

结合标题可以确定的关键点是：移除动作同时发生在 Chrome 与 Edge，且文章对影响面做了分层讨论。至于具体移除的是哪个版本范围、是否可通过 flag 或企业策略回退、是否同步影响无头模式与移动端，**原文未说明**。

以下是通用背景推演，**不代表原文结论**：

- 客户端 XSLT 常见于旧式企业内网、政府与文档类站点、RSS/Atom 样式化渲染、以及部分设备与协议配置文件的展示场景。
- 一旦浏览器不再执行 XSLT，相关页面可能退化为直接展示原始 XML 树，或依赖 `xml-stylesheet` 的渲染完全失效。
- 常见替代路径包括：服务端预转换、构建期静态转换、或改用 JavaScript 侧的 XML 解析与模板渲染。

## 对数据科学 / AI Agent 落地的意义

这一变更与数据科学、AI Agent 并非直接相关，影响主要体现在数据获取与转换链路上。以下为笔者基于通用经验的推断，**原文未就这些场景展开**：

- **数据管道重心上移**：不少行业接口与遗留系统仍以 XML 为主要交换格式，XSLT 曾是成本极低的转换层。浏览器端能力移除后，转换逻辑会更集中地落在服务端 ETL、数据集成平台或流处理层，这反而有利于可测试性与版本管理。
- **Agent 抓取与渲染工具链**：当 AI Agent 依赖无头浏览器访问遗留 Web 系统时，若目标页面依赖客户端 XSLT 渲染，Agent 拿到的是原始 XML 而非可读内容。这意味着抓取工具需要自带 XML 解析/转换能力，或在渲染层准备兼容策略。
- **回归测试与数据质量**：涉及 XML 展示的站点应补充端到端用例，避免数据本身没问题、但呈现层失效导致的误判。

## 我的技术点评

第一，浏览器淘汰 XSLT 更像是平台持续瘦身的延续，与此前对插件、旧 API 的清理逻辑一致。真正的风险不在主流站点，而在长尾的遗留系统和内部工具——它们往往缺人维护，也最容易被"悄悄坏掉"。

第二，文章的切题方式值得肯定。标题强调"what breaks and what does not"，说明影响是分层的而非一刀切。对工程团队而言，正确的动作不是恐慌性重写，而是先盘点：站内是否存在 `xml-stylesheet` 引用、是否有依赖浏览器执行 XSLT 的展示路径、这些路径是否在关键业务链路上。

第三，对数据工程与 Agent 实践者，这是一次老提醒：不要把关键的数据转换能力寄托在浏览器行为上。把转换放到服务端或数据管道中，才能做到可版本化、可回归、可替换。
