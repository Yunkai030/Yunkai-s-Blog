## 一、事件与产品概述

Hacker News 首页出现了一个名为 **EyesRhythm** 的 Show HN 项目（25 points，11 条评论），定位是"离线桌面伴侣"，帮助长时间盯屏的人维持健康的眨眼节律。产品支持 macOS 与 Windows，当前版本 1.6.0（macOS 安装包 93 MB，Windows 安装包 85 MB），免费下载，无需账号、无需 license key。

它的出发点不是技术演示，而是一段真实的职业损伤自述：作者自称做了约 20 年计算机视觉方向的研究工程师，长期放大到像素级细节手工设计算法，最终出现干眼问题，医生的结论是只能靠规律使用人工泪液维持。产品页的 About 部分则表述为"二十余年软件开发"，并提到干涩、发红和明显不适。原文两处表述略有出入，但核心一致：这是从个人痛点长出来的工具。

产品解决的问题有明确的生理背景：专注用屏时眨眼频率常常下降到正常水平的一半左右，而**稀疏且不均匀**的眨眼是数字视疲劳、干眼、异物感、视物模糊的已知诱因，且往往在眼睛已经疼了之后才被察觉。

值得注意的是，官方反复声明它**不是医疗器械**，不提供诊断或治疗，持续性不适应当交给眼科专业人士。

## 二、关键技术点

**1. 全本地推理，视频不出机器。** 摄像头帧在本机读取后即丢弃，不上传、不保存人脸影像。没有账号体系、没有云端、没有 license 和内嵌分析上报，今日统计与偏好设置只落在本地文件夹。这是产品架构的前置约束，而不是事后补的隐私声明。

**2. 多摄像头自动追踪面部。** 桌面可能同时接了多个摄像头，EyesRhythm 能自动在多个摄像头之间选择/切换，以取得最利于眨眼检测的眼部视角。具体的选择策略与切换逻辑，原文未说明。

**3. 眨眼事件检测。** 通过内置摄像头或 USB 摄像头识别每一次眨眼，输出每分钟眨眼次数。底层用的是哪类人脸关键点模型、分类器或时序判定规则，以及是否区分左右眼、如何处理戴眼镜场景，原文未说明。

**4. 从"计数"到"节律"：ORI 指标。** 这是产品在指标设计上最有想法的一点。官方明确指出，单纯的 blink counter 不够：同样 6 次眨眼，如果集中在短时间内爆发、中间夹着一段长时间不眨，和均匀分布是两种完全不同的眼部状态。EyesRhythm 把两个维度合并成一个 **Ocular Rhythm Index（眼动节律指数，0–100）**：

- **Rate（频率）**：多久眨一次；
- **Regularity（规律性）**：眨眼的间隔是否稳定。

频率够但呈"阵发+干旱"模式，仍然会让眼表干燥；频率偏低但分布均匀，同样不理想。ORI 的具体归一化方式、权重、滑动窗口长度与评分曲线，原文未说明。

**5. 实时反馈闭环。** 提示默认常开，视觉形式是一段安静的橙色脉冲，点击 A 可切换为声音；B 键可以开启"每次眨眼滴答一声"的更紧反馈回路，让用户对习惯的感知更直接。此外还有最近 5 分钟眨眼节律的实时曲线，以及屏幕时间、FPS（界面显示 30）、视线角度等常驻数值。

**6. Practice 引导练习。** 一个两分钟倒计时式引导会话，用节奏带动眨眼，目的是建立肌肉记忆。

**7. Poise：颈部姿态的"另一半"。** 表盘按 30° 分片记录今天头部转向过哪些方向：绿色是看过最多的方向，红色是几乎没用的方向。长时间电脑作业会把颈部锁在单一姿势，Poise 用覆盖度可视化提醒用户上、下、左、右转动，让颈肩放松后再回到屏幕。官方同样强调这是提醒，不是治疗。

**8. 轻量 GUI 形态。** 紧凑窗口贴在工作区旁边，只在实际面对屏幕时计数；设置与报告可以停靠在旁边，摄像头预览默认收起，打开 Lens 才显示。

## 三、对数据科学与 AI Agent 落地的意义

这个产品虽然体量小，但在方法论上有几点对数据科学和 Agent 落地挺有参考价值。

**第一，指标设计比模型更重要。** 眨眼检测本身是个成熟的 CV 任务，真正体现产品判断的是把"频率 + 规律性"折叠成一个 0–100 的可比较分数。这与我们在业务里做健康度评分、用户活跃度评分、模型漂移评分是同一类问题：单一计数型指标（次数、点击数、请求数）容易被"聚集效应"欺骗，必须引入间隔分布的离散程度。眨眼间隔序列本身就是一个典型的时间序列，可以用变异系数、间隔熵、分位数差等刻画"均匀性"——但需要说明，**EyesRhythm 实际采用的计算方式原文未说明**，上述只是同类问题的一般做法。

**第二，端侧优先的隐私架构正在成为默认选项。** "帧本地读取后丢弃、无账号、无云、无 analytics"这套组合，让一个涉及摄像头和面部的应用可以在不触碰合规红线的前提下分发。对做 Agent 的团队来说，这意味着感知层（摄像头、麦克风、屏幕内容）可以留在本地，只有脱敏后的聚合指标（ORI、屏幕时间、转向覆盖度）才具备被进一步利用的价值。这是一个很干净的"原始数据不出端、特征/指标可流动"的分层范式。

**第三，反馈型 Agent 的告警设计。** EyesRhythm 的提示策略值得抄：默认开启但极度克制（安静橙色脉冲），声音是可选，逐次眨眼的滴答声是再下一层可选。这正是 Agent 落地里最难的部分——如何在"提醒有效"和"打扰用户"之间取平衡，避免告警疲劳导致用户直接关掉整个功能。分层可调、默认低干扰，是可持续人机协同的基本形态。

**第四，长期陪伴型 Agent 的形态参考。** 这个产品可以视作一个极简的"健康守护 Agent"：常驻感知 → 计算指标 → 在阈值或模式异常时给轻量反馈 → 记录日志供回看。它没有大模型、没有对话，但在"持续观察 + 少量干预"这条路径上是完整闭环的。未来若叠加自然语言总结（例如"你今天下午的眨眼间隔明显变长"），就是典型的端侧小模型 + 本地感知 Agent 组合。当然，这部分属于延伸设想，**原文未提及任何 LLM 或生成式能力**。

## 四、我的技术点评

**做得好的地方：**

- **痛点真实，切口极小。** 没有做"全能健康助手"，只做眨眼节律加一个颈部转向表盘，功能边界清楚，避免了同类工具常见的仪表盘膨胀。
- **指标思路有见地。** 明确反对"只数次数"，把规律性纳入评分。这是对领域问题有理解才会做出的设计选择，而不是套一个通用计数器。
- **隐私是一等公民而非营销词。** 无账号、无 key、无云、无分析、帧不留存，这组约束会直接限制产品能做的事情，说明它是被当作架构前提而非宣传语。
- **提醒的分级设计克制。** 视觉默认、声音可选、逐次滴答再可选，把打扰强度交给用户。

**需要保留的地方：**

- **ORI 缺乏公开定义与验证。** 0–100 的分数看起来专业，但公式未公开，也没有任何与临床量表、眨眼间隔统计量的对照数据。作为一个自评工具够用，作为"健康指标"则需要证据。原文只给出了"频率 + 规律性"的定性描述。
- **检测精度未知。** Webcam 眨眼检测在戴眼镜、逆光、侧脸、低照度下的鲁棒性，界面显示 30 FPS 对一次可能只有一两百毫秒的眨眼是否足够，误检与漏检率如何，原文均未说明。而这直接决定 ORI 的可信度。
- **"100% 本地"依赖厂商自述。** 产品免费但不开源，本地性只能靠声明与隐私页背书，无法被第三方验证。对隐私敏感用户来说，开源或提供可复核的网络行为说明会更有说服力。
- **缺少纵向效果证据。** 没有使用前后对比、没有用户研究数据，Practice 是否真的建立肌肉记忆、ORI 提升是否对应症状缓解，目前都是产品假设。
- **热度仍是早期。** HN 25 points、11 条评论，属于小范围曝光，社区反馈样本很有限。
