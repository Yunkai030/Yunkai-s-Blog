## 论文概述

arXiv 新论文 **《Together Compiler: Continual Compilation for AI Inference》**（arXiv:2611.14681）提出 **Together Compiler（TKCC）**，目标是解决 AI 推理部署中的持续优化问题。

论文指出，当前 AI 工作负载变化很快：新模型发布更频繁、模型架构更加多样、流量分布也经常变化。对推理系统而言，把一次部署编译成优化后的前向计算过程，并不是一次性任务，而是一个需要持续迭代的过程。作者认为，这类问题很适合用 **Agent 爬山式优化** 来解决，但现有系统面临一个核心矛盾：**测量吞吐与测量保真度之间的权衡**。

具体来说，很多系统让 Agent 基于离线基准优化单个 kernel，但由于 MoE 等算子的行为依赖数据分布，离线计时保真度较低；另一类系统让 Agent 直接优化端到端引擎，却又受制于引擎启动时间过长，难以支撑持续编译。为此，作者构建了 TKCC，并称其为**首个真正面向 AI 推理优化的持续 Agent 循环**。

## 关键技术点

论文的核心设计围绕“如何让 Agent 持续、高频且高保真地优化推理系统”展开，主要包括以下技术点：

1. **Tiered Persistent Engine：分层持久化引擎**

   TKCC 通过分层持久化引擎，将引擎启动开销与前向计算解耦。这样做的目的是减少端到端引擎反复启动带来的测量瓶颈，使 Agent 能够在更接近真实推理的条件下持续评估和优化。

2. **成本模型选择并行配置**

   论文提出使用成本模型选择并行配置，并将这些配置作为优化过程的初始种子。换言之，系统不是完全盲目地搜索并行策略，而是先用成本模型缩小搜索空间，再由 Agent 继续爬山优化。

3. **面向推理前向过程的 Agent 优化循环**

   TKCC 将编译部署视为一个持续优化的 Agent 循环。Agent 在真实或近似真实的推理反馈中不断调整优化方案，而不是仅依赖离线 kernel 基准。

4. **Agent 上下文管理消融**

   作者对 Agent 上下文管理进行了较广泛的消融实验，并总结了在生产环境部署 TKCC 的经验。原文摘要提到了这些实验和部署洞察，但具体上下文策略细节在摘要中未展开。

5. **性能结果**

   根据摘要，TKCC 在 Llama 1B 主力工作负载上，相比高度优化的人工编写 Megakernels 最高提升 **1.7 倍**；在 InferenceX 基准上，针对 Kimi K3、GLM 5.3、MiniMax M3.1 Flash、DeepSeek v4.1 Flash 等最新前沿模型，跨硬件平台相比最佳开源引擎最高实现 **2.6 倍 TPS**。此外，TKCC 在 batch size 为 1 时达到作者所称的 SOTA：MiniMax M3.1 Flash 上 **1111 TPS**，DeepSeek v4.1 Flash 上 **1205 TPS**。作者还表示，TKCC 已在其生产集群中服务数万亿 tokens，并可推广到前沿语言模型推理之外。

## 对数据科学与 AI Agent 落地的意义

这篇论文的价值不只在“推理加速”，更在于它展示了一种 **Agent 与系统级优化深度结合** 的落地范式。

对数据科学和 AI 工程团队而言，模型与流量分布持续变化意味着性能优化不能只做一次。传统做法往往依赖人工调参、离线基准和阶段性上线验证，而 TKCC 的思路是把“测量—优化—验证”做成持续循环。这对推荐系统、搜索、生成式 AI 服务等动态负载场景都有参考意义。

对 AI Agent 落地来说，论文强调了一个容易被忽视的问题：**Agent 的优化能力上限，很大程度上取决于反馈信号的质量和获取速度**。如果测量保真度不足，Agent 可能优化了错误目标；如果每次测量都太慢，Agent 又无法持续迭代。TKCC 通过持久化引擎和成本模型先验，试图同时改善反馈保真度与搜索效率。这比单纯增加 Agent 推理步数更有工程价值。

不过，原文摘要没有说明 TKCC 是否开源、具体支持哪些硬件平台、成本模型的细节以及完整基准设置。因此，其生产收益能否在更多团队和更多模型上复现，仍需进一步验证。

## 我的技术点评

我认为 TKCC 最值得关注的地方，是它把 Agent 优化从“让模型写 kernel”推进到了“让 Agent 持续参与推理系统编译与调优”。这背后的关键不是 Agent 本身，而是 **测量基础设施**：分层持久化引擎让高频测量成为可能，成本模型则为搜索提供先验，二者共同缓解了 Agent 优化中常见的“反馈慢、反馈不准”问题。

从工程角度看，这是一个比较务实的方向。很多 Agent 优化系统在 Demo 中表现不错，但进入生产后会受限于启动开销、数据依赖和长尾流量。TKCC 明确针对这些系统瓶颈设计，而不是只做算法层面的搜索策略改进，这一点值得肯定。

需要保持谨慎的是，论文摘要给出的主要是 TPS 和相对加速比，尚未说明延迟分位数、成本、能耗、不同流量模式下的稳定性，以及 Agent 循环长期运行时的回归风险。对于生产推理系统而言，持续编译还必须配套回滚机制、质量监控和成本约束。总体来看，TKCC 为“持续编译 + Agent 优化”提供了一个有代表性的系统样本，但它的实际通用性仍取决于更多独立复现和生产验证。
