## 论文概述

arXiv 新论文《Cleaning an Agent's History Hurts When the World Still Holds the Error》讨论了一个容易被忽略的 Agent 工程问题：工具调用型语言模型 Agent 会在历史中积累自己的错误，而压缩、修复或交接这些历史时，系统实际上是在决定“如何描述这些错误”。问题在于，错误的副作用可能仍保留在外部世界中。

论文作者为 Egor Pakhomov、Anurag Koul、Hongjun Liu、Bo Pang、Shafiq Joty、Erik Nijkamp，提交于 2026 年 11 月 10 日，属于 cs.AI，同时涉及 cs.CL 和 cs.LG。论文共 23 页、6 张图，代码和数据放在 ancillary files 中。

既有工作通常在“固定世界”下清理历史，即展示一个纠正步骤和宣称任务完成是同步发生的。本文则进一步追问：同样的正确内容，是否会因为历史表述方式和世界当前状态不同，而产生帮助或伤害？

## 关键技术点

论文采用的核心方法是：把 Agent 冻结在任务中途，保留其精确的世界状态，然后分别编辑历史或世界，再让接收模型（receiver model）继续执行任务。

在 AgentCE-Bench 上，实验让 Agent 先提交一个错误值，然后保持世界不变，通过两种自然方式加入正确值：

- 在保留错误的同时，添加一条真实注释；
- 把该值表述为 Agent 自己已经完成的动作。

结果显示，真实注释将恢复率从匹配中性注释条件下的 51% 提升到 66%。这里的恢复率指接收模型在剩余目标中做对的比例。相反，把正确值表述为“已完成动作”会把恢复率从 50% 降到 44%，甚至低于未编辑历史。这说明，仅仅让正确值出现在历史中，并不能预测它会产生正面效果。

在 AppWorld 上，实验围绕一次数据库写入展开，分别改变回执是否报告成功或失败，以及写入效果是否真实存在。结果发现：当效果不存在时，成功回执会把整任务成功率从 45% 降到 28%；当效果存在时，成功回执则会把成功率从 38% 提升到 49%。原文报告，这两个效应在两名接收模型合并后相差 27 个百分点；在八个接收模型中，97.5% 水平上有六个为正，95% 水平上有七个为正。

论文的结论是：历史编辑的效果取决于它所描述的世界状态。一个看起来“干净”的历史，如果世界仍然保留着错误，可能让 Agent 比不编辑更糟。

## 对数据科学或 AI Agent 落地的意义

这项工作对 Agent 记忆管理、上下文压缩、任务交接和错误恢复都有直接警示。生产系统中的 Agent 经常需要压缩历史、修复错误步骤或把任务移交给另一个模型；如果只修改历史文本，却没有同步修复数据库、文件系统、外部 API 状态或其他副作用，接收模型可能基于“已经完成”的叙述继续行动，从而放大错误。

对数据科学实验而言，论文也强调了一个重要原则：评估历史编辑效果时，不能只控制历史内容，还必须控制世界状态。否则，“正确内容”的效应会与“世界是否已经改变”混在一起，导致结论不可迁移。

对 AI Agent 落地而言，更稳妥的做法是把“历史一致性”和“世界一致性”分开检查：该回滚的要回滚，该重试的要重试，该保留错误证据的要保留，并在交接时明确说明哪些副作用尚未修复。原文未说明具体接收模型型号和完整任务细节，因此工程团队仍需结合自身工具链验证。

## 我的技术点评

这篇论文最有价值的地方，是把“上下文工程”里一个常见但含糊的直觉拆成了可测量的问题：历史写得对，不等于世界状态对；历史写得干净，也不等于 Agent 会更安全。尤其是“真实注释”与“已完成动作”两种表述的差异，说明语言层面的语用信息会显著影响后续决策。前者保留错误并补充事实，后者则可能让接收模型误以为副作用已经处理完毕。

从落地角度看，Agent 系统不应把历史清理当成纯文本压缩任务，而应把它当成状态同步协议的一部分。历史压缩、错误修复和任务交接都需要回答三个问题：世界上发生了什么、历史如何描述它、接收方接下来应该相信什么。若三者不一致，再漂亮的历史也可能成为新的故障源。
